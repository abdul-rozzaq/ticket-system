## Deviations from the specification (P3/P4/P5/P6)

1. **No BullMQ/Redis for intake or userbot commands.** The debounce buffer is a PostgreSQL table (`IntakeBuffer`, atomic
   append and claim) polled every 5 s, and userbot commands are a PostgreSQL outbox the userbot long-polls over HTTP
   (`FOR UPDATE SKIP LOCKED`). Reason: restart-safe, no extra moving part, and fully testable end to end. Redis/BullMQ
   remains planned for reminders/digests/folder reconcile (P4/P5).
2. **zod instead of class-validator**, so request schemas are shared with the admin panel and extension.
3. **P4:** the bot long-polls a PostgreSQL outbox (like the userbot) instead of BullMQ; reminders run on a 30 s timer inside the API (`BOT_POLL_MS`) with unique dedupe keys.
4. **P5:** Telegram refuses folders without chats, so empty funnel folders hold a "Saved Messages" placeholder by default (`funnel.emptyFolders=remove` deletes them instead). A sync holds one DB transaction (advisory lock) for its duration.
5. **P6:** retrieval does not use `KbChunk` text for full-text search (it searches the article text; the GIN index matches that expression); chunks exist for vectors. Draft model prompts are English while drafts follow the customer's language. Embeddings need an OpenAI-compatible provider.
6. **Claimed-then-crashed userbot commands** are not re-queued automatically yet (a command claimed by a userbot that dies stays
   `CLAIMED`). Low impact (all commands are idempotent or user-retriable) but worth a sweeper in P8.

## Honest summary

Roughly 40 % of the specification exists. The backend core and the whole userbot/intake logic are real and tested
against fakes; **nothing has touched a real Telegram account or a real AI provider**. The bot, folders, admin panel, KB/RAG
and the extension integration are not built.

## Open risks

1. **Telegram ToS / ban risk.** A userbot on the single shared TP account can get it limited or banned, and the whole
   workflow depends on it. Mitigations in code: rate limiter, FLOOD_WAIT back-off, no automatic sending, deletes only own
   messages (the adapter checks `out`). Test on a throwaway account first; consider Telegram Premium.
2. **Folder limits** (10 folders / 100 chats per folder, 20 / 200 with Premium): the logic degrades to system folders and warns (tested); recommend Premium.
3. **Telegram Web DOM drift** for the extension (selectors isolated in `selectors.ts`).
4. **AI cost / privacy.** Masking before every call, budget hard stop and fail-open are implemented; real cost per message is unmeasured. Current Claude models reject custom `temperature`, so the Anthropic adapter never sends it.
5. **Shared-account attribution** of who answered is heuristic (extension ping within 15 s before the send): confidence 0.9 for one active person, 0.5 for several, none otherwise.
6. **Single API instance assumption**: domain events are in-process; auto-assign/realtime run in the instance that handled the request. Fine for one container, needs Redis fan-out before scaling out.
7. **Debounce poller** runs inside the API process; with several API instances processing is still safe (atomic claim) but not coordinated.
