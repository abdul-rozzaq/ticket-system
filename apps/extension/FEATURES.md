# Features F1–F18: what they do, how they work, and what to keep

**How to read "Status".** Three levels of evidence exist in this prototype:

- **Unit** — pure logic covered by Vitest (`pnpm test`, 41 tests).
- **Harness** — the built `content.js` was run in Chromium against a *fake* Telegram page (`harness/`, written from memory of Telegram's DOM) and the feature behaved as expected.
- **Real Telegram** — always `NOT_TESTED`. Nobody has run this against the live web.telegram.org yet. Run [MANUAL_TESTS.md](MANUAL_TESTS.md).

Fragility is about breakage when Telegram ships a new web build: **low** (no Telegram DOM), **medium** (one or two selectors), **high** (deep DOM structure or Telegram's internal behaviour).

## What this tells us about the real product

**Must stay in the extension** (only the browser can do it):

- Knowing which chat is open (F1, URL hash) and showing context next to it (F2/F15, F3).
- Putting text into the composer without sending (F6) and the fast-entry UX around it: `;` templates (F5), hover actions (F8), palette (F12).
- Light, read-only helpers on top of the page: chips (F10), maybe chat-list dots (F11).
- A local masking pass before anything leaves the browser (F13), duplicated on the server.

**Should move to the backend** (NestJS + Prisma + GramJS + internal bot):

- Tickets, statuses, assignments, SLA clocks, history and notes (F3/F4/F16) — one source of truth for 2–3 people sharing one Telegram account; the extension becomes a thin client calling an API.
- Reading messages (F7): the GramJS userbot sees every message, with ids, senders and reply chains, without DOM scraping. Ticket creation should be triggered there, not by the extension.
- Knowledge base, retrieval and LLM calls (F9): keys off the browsers, shared KB built from "Hal bo'ldi" solution notes, audit log, cost control.
- Reminders and SLA alerts (F14): via the internal bot so they reach whoever is on duty, not one browser.
- Stats (F17) → admin panel.

**Riskiest assumptions to verify first** (MANUAL_TESTS.md sections 2, 3, 5): composer insertion strategy per client, the `;` trigger not being eaten by Telegram's own key handling, and whether insertion still works from the side panel. If insertion from the side panel works, the side panel is the more robust main surface.
